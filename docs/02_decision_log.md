# 02 — Decision Log

Every major technology or design decision is recorded here (required by the project brief).
Status: **Accepted** / **Proposed** / **Open**.

| ID | Decision | Options considered | Reason | Status | Day |
|---|---|---|---|---|---|
| D-001 | Workflow = HR resume screening | Invoices, ticket routing, lead qualification | Mix of safe and high-risk steps; fully synthetic data possible; measurable ground truth | Accepted | 1 |
| D-002 | Language = Python | — | Ecosystem for LLM APIs, Pydantic, FastAPI, Streamlit | Accepted | 1 |
| D-003 | Workflow representation = JSON spec validated by Pydantic; this is the single source of truth | DAG library, state machine, n8n JSON | Portable, testable, easy to diff for versioning, supports steps/branches/conditions/exceptions/approvals | Accepted | 1 |
| D-004 | Executor for generated automation | LangGraph vs custom DAG runner | Decide on Day 7 after the spec is stable. Shadow mode needs step-level interception of tool calls | Open (Day 7) | 1 |
| D-005 | n8n = optional export target only | Use n8n as primary executor | Shadow mode, confidence, comparison and approval gates are easier to control in our own code. Export to n8n JSON is a stretch goal if time remains | Proposed | 1 |
| D-006 | Storage = SQLite | PostgreSQL | Zero setup, enough for a mock environment | Proposed | 1 |
| D-007 | API layer = FastAPI | — | Named in brief; simple typed endpoints | Proposed | 1 |
| D-008 | Dashboard = Streamlit | React, Next.js | Fastest path to a working dashboard; brief allows it | Proposed | 1 |
| D-009 | LLM provider = Groq | OpenAI, Anthropic, local models | Confirmed by user Day 2. Exact model to be pinned once mock environment + prompts exist (Day 3+), checking Groq's current model list and rate limits at that time | Accepted | 2 |
| D-010 | Data = synthetic only | Anonymised real data | Removes privacy risk entirely (S1) | Accepted | 1 |
| D-011 | Git convention: one commit per day (`dayNN: summary`) plus tag `day-NN` | Feature branches | History mirrors the 15-day plan; simple to review | Accepted | 1 |
| D-012 | Result files generated by scripts only | Hand-written tables | Prevents fabricated metrics (S7) | Accepted | 1 |
| D-013 | Event schema uses nested typed sub-objects (`DecisionRecord`, `ExceptionRecord`) rather than free-text fields | Free-text `decision`/`exception` strings | Lets Day 6 (rule extraction) and Day 11 (exception handling) query structured data instead of parsing prose | Accepted | 2 |
| D-014 | AI-shadow events reuse the same `Event` schema as human events, distinguished by `actor_type` | Separate `AIEvent` type | Keeps Day 9 comparison a simple filter/join instead of a translation layer between two schemas | Accepted | 2 |
| D-015 | Confidence field is enforced (by a Pydantic validator) to be null on human events | Convention only, no enforcement | Prevents a logging bug from quietly mixing human and AI confidence data | Accepted | 2 |
| D-016 | Faults are injected via an explicit `fault:` parameter on every mock-tool method, raising typed exceptions | Random failure injection | Deterministic and repeatable — required for exact, reproducible failure-case tests (Day 14) rather than flaky randomness | Accepted | 3 |
| D-017 | `send_email` hard-requires `approved=True` and only ever writes to an in-memory outbox; no SMTP/network code exists in the module | Trust the approval gate (Day 11) alone to prevent real sends | Code-level backstop for Safety rule S3 — irreversible action is structurally impossible here, not just policy-guarded | Accepted | 3 |
| D-018 | Ground truth for the 12 synthetic resumes is hand-labelled by us and stored in `data/ground_truth.json`, explicitly marked as a test fixture, not an experimental result | No ground truth; only measure agreement, not accuracy | Needed so Day 5 reconstruction and Day 13 readiness evaluation have something concrete to score against, without it being confused with real experiment output (S7) | Accepted | 3 |
| D-019 | Event logger separates "record what happened" (`EventLogger`) from "decide what to do" (`HumanDemoPolicy`) | One combined logger+policy class | The same logger will wrap the AI shadow engine's actions on Day 8 unchanged — only the decision layer differs between a human demo and a shadow run | Accepted | 4 |
| D-020 | Human demo policy's skill-match tiers are documented as our own data-generation design, not a claimed learned/discovered rule | Present the policy as if it were extracted from data | Prevents Day 6's decision-extraction accuracy from trivially "rediscovering" its own generator — extraction must be evaluated as a genuinely separate step | Accepted | 4 |
| D-021 | Demonstration dataset (`data/demonstrations.json`) is generated exclusively by running `build_dataset.py`, never hand-edited | Hand-author some demo events for variety | Keeps every event traceable to actual code execution (S7); reproducible by re-running the script | Accepted | 4 |
| D-022 | Reconstruction excludes `demo_dup_*` and `demo_fault_*` demonstrations before building workflow structure | Feed all demos to the reconstruction engine unfiltered | Those demos contain deliberately artificial post-completion/fault events (Day 4) that create spurious edges (e.g. `send_interview_invitation -> fetch_resume`); they belong to exception-handling testing (Day 11), not workflow-shape discovery. Proven with a negative-control test that shows the pollution when the filter is skipped | Accepted | 5 |
| D-023 | Reconstruction merges one node per distinct action name across all demos (not one node per demo-step) | Keep each demo's steps separate, then union by position | Produces an actual structured workflow rather than a replay of 12 separate logs — this is what "identify relationships between events" (Section 6) means in our design | Accepted | 5 |
| D-024 | Reported finding: this dataset contains no true multi-way branch (a step with 2+ distinct next actions); `update_candidate_record`'s continuation to `send_interview_invitation` is optional, not a fork | Force the test/design to assume a branch exists | Reconstruction results must be reported honestly, including a null finding — inventing a branch that isn't in the data would violate S7 | Accepted | 5 |
| D-025 | A rule counts as EXPLICIT only if its condition maps directly onto a field already present in `job_description.json`'s explicit configuration (required_experience_years, required_skills) | Call anything with 100% consistent evidence "explicit" | Matches Section 4's "explicit policy configuration" and Section 8's own example ("required_skill_present"); consistency in data is evidence for INFERRED, not grounds to call something explicitly stated | Accepted | 6 |
| D-026 | INFERRED requires >= 2 independent, consistent supporting demonstrations (`MIN_EVIDENCE_FOR_INFERENCE`); a single consistent example is labelled UNKNOWN, not inferred | Treat any single-example, non-contradictory pattern as inferred | With only 12 demos, most edge-case evidence combinations have exactly 1 example — calling that "inferred" would fabricate confidence the data doesn't support (Section 38) | Accepted | 6 |
| D-027 | Decision extraction (`decisions/extraction.py`) reads only `demonstrations.json` + `job_description.json`; it does not import `logger/human_demo.py` | Have extraction call into or reuse the Day 4 generator's logic | Keeps extraction accuracy a genuine measurement rather than the generator re-discovering its own rules — enforced by a structural test that parses the module's AST for imports | Accepted | 6 |
| D-028 | The prompt-injection override (res_0012) is extracted as UNKNOWN (n=1), not treated as a known safety rule | Hard-code the engine to recognize this case as a deliberate policy | The extraction engine only sees events + explicit JD config; the injection-override policy isn't exposed as config anywhere it can check, so UNKNOWN is the honest answer from the evidence available — flagged as a design question for later days (should injection-handling become declared policy?) | Accepted | 6 |

## Notes

- Avoid unnecessary complexity: add a framework only if it earns its place.
- When a decision changes, add a new row or update the status. Do not silently delete history.

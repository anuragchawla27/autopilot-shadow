# 02 — Decision Log

Every major technology or design decision is recorded here (required by the project brief).
Status: **Accepted** / **Proposed** / **Open**.

| ID | Decision | Options considered | Reason | Status | Day |
|---|---|---|---|---|---|
| D-001 | Workflow = HR resume screening | Invoices, ticket routing, lead qualification | Mix of safe and high-risk steps; fully synthetic data possible; measurable ground truth | Accepted | 1 |
| D-002 | Language = Python | — | Ecosystem for LLM APIs, Pydantic, FastAPI, Streamlit | Accepted | 1 |
| D-003 | Workflow representation = JSON spec validated by Pydantic; this is the single source of truth | DAG library, state machine, n8n JSON | Portable, testable, easy to diff for versioning, supports steps/branches/conditions/exceptions/approvals | Accepted | 1 |
| D-004 | Executor for generated automation | LangGraph vs custom DAG runner | Decide on Day 7 after the spec is stable. Shadow mode needs step-level interception of tool calls | Open (Day 7) | 1 |
| D-005 | n8n = optional export target only | Use n8n as primary executor | Shadow mode, confidence, comparison and approval gates are easier to control in our own code. Export to n8n JSON is a stretch goal if time remains | Proposed | 1 |
| D-006 | Storage = SQLite | PostgreSQL | Zero setup, enough for a mock environment | Proposed | 1 |
| D-007 | API layer = FastAPI | — | Named in brief; simple typed endpoints | Proposed | 1 |
| D-008 | Dashboard = Streamlit | React, Next.js | Fastest path to a working dashboard; brief allows it | Proposed | 1 |
| D-009 | LLM provider = Groq | OpenAI, Anthropic, local models | Confirmed by user Day 2. Exact model to be pinned once mock environment + prompts exist (Day 3+), checking Groq's current model list and rate limits at that time | Accepted | 2 |
| D-010 | Data = synthetic only | Anonymised real data | Removes privacy risk entirely (S1) | Accepted | 1 |
| D-011 | Git convention: one commit per day (`dayNN: summary`) plus tag `day-NN` | Feature branches | History mirrors the 15-day plan; simple to review | Accepted | 1 |
| D-012 | Result files generated by scripts only | Hand-written tables | Prevents fabricated metrics (S7) | Accepted | 1 |
| D-013 | Event schema uses nested typed sub-objects (`DecisionRecord`, `ExceptionRecord`) rather than free-text fields | Free-text `decision`/`exception` strings | Lets Day 6 (rule extraction) and Day 11 (exception handling) query structured data instead of parsing prose | Accepted | 2 |
| D-014 | AI-shadow events reuse the same `Event` schema as human events, distinguished by `actor_type` | Separate `AIEvent` type | Keeps Day 9 comparison a simple filter/join instead of a translation layer between two schemas | Accepted | 2 |
| D-015 | Confidence field is enforced (by a Pydantic validator) to be null on human events | Convention only, no enforcement | Prevents a logging bug from quietly mixing human and AI confidence data | Accepted | 2 |

## Notes

- Avoid unnecessary complexity: add a framework only if it earns its place.
- When a decision changes, add a new row or update the status. Do not silently delete history.

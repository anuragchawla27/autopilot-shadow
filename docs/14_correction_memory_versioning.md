# 14 — Correction Memory and Workflow Versioning (Day 12)

## 1. What this component does — Sections 24, 25

**Section 24** asks for stored correction data (Original AI Decision,
Human Correction, Evidence, Workflow Context, Reason, Timestamp) and
explicitly says: "Do not blindly retrain a model on every correction."
**Section 25** asks for workflow versions tracked over time (its own
example: Manual → Partially automated → Human-in-the-loop →
High-confidence automation), with changed steps/rules/risk/agreement/
outcomes tracked between them.

## 2. Correction memory — honest about what data actually exists

This project has no live human-in-the-loop UI yet (Day 14 builds the
dashboard). Nobody has clicked approve/edit/reject/escalate on a real
case, so there is currently **no genuine correction data** to store —
same honest situation as Day 9's 0 disagreements and Day 11's 0
disagreement records.

Rather than stop at "0 real corrections, mechanism untested against
real shapes," this day's build script (`correction/build_correction_memory.py`)
applies a small, fixed, fully-visible reference policy
(`simulate_decision`) to Day 11's real 16-item approval queue, and
stores the results tagged `source="simulated_demo"` on every single
record. This is a demonstration that the storage/retrieval mechanism
works end-to-end against real queue shapes — **it is not an evaluation
result and must never be read as real human-agreement or
correction-rate data.** The actual proof the mechanism is correct comes
from the hand-built synthetic test cases (same pattern as Days 9 and
11), not from this demo run.

**The reference policy, in full** (nothing hidden): `approval_required`
cases (the hard Section 22 override) are escalated, never
auto-approved, even in a simulation. `human_review` cases (failed
extractions) are rejected — there's no usable data to approve.
`automate_with_monitoring` cases are edited with an added monitoring
note. An `approve` decision is never simulated by this policy on
purpose — Section 24's "correction" concept only applies when the human
changed something; recording approvals here would misrepresent the
store as containing real agreement data.

**Why `approve` never produces a stored record, structurally:**
`correction/from_approval.py`'s `correction_from_outcome` returns `None`
for `decision == "approve"` — proven directly by
`test_approve_decision_never_becomes_a_correction_record`. A correction
store is for corrections, not for every decision made.

**Retrieval design**: `CorrectionMemory.retrieve_similar(action,
top_n)` is a plain, most-recent-first lookup keyed by action — not
semantic/embedding search. Section 24 itself lists several possible
uses for stored corrections (retrieval-based memory, rule updates,
prompt/context updates, eval dataset expansion, model adaptation) and
explicitly warns against the most complex one (blind retraining).
Plain retrieval is the simplest mechanism that satisfies the
requirement — same "avoid unnecessary complexity" reasoning Day 7 used
to skip LangGraph (D-004).

## 3. Workflow versioning — four versions, all but one already real

`versioning/workflow_version.py` defines the brief's own 4-tier
progression, mapped onto this project's actual build history, with
every metric pulled from a real results file this project already
generated:

| Version | Label | Built | Reached? | Key metric |
|---|---|---|---|---|
| V1 | Manual | Day 4 | Yes | 68 human events, 12 resumes, 0% automation |
| V2 | AI-Proposed (Shadow) | Day 8 | Yes | 74 AI proposals, 0% executed (shadow never commits) |
| V3 | Risk-Aware Human-in-the-Loop | Day 11 | Yes | 78.4% automation coverage, 21.6% gated |
| V4 | High-Confidence Automation | Day 13 (target) | **No** | — |

V4 is honestly left empty (`reached=False`, `metrics={}`) rather than
invented — proven by `test_v4_metrics_are_honestly_empty_not_fabricated`.
Section 26 (Day 13's readiness assessment) is where this project will
actually decide, from evidence, whether any step qualifies for this
tier.

`versioning/version_diff.py` diffs two versions generically — whatever
keys exist in either version's `metrics` dict, not a hand-listed set of
"the fields that happen to differ between V2 and V3." This means a
future V5 is diffable without touching this module.

remove/change detection plus the `reached` state-change flag and the

## 6. What Day 13 builds on top of this

Day 13 (automation-readiness evaluation, Section 26) reads
`results/day12_workflow_versions.json` and `results/day12_version_diffs.json`
directly — V3's real coverage/risk numbers are the evidence Section 26
needs to actually decide whether V4 ("High-Confidence Automation") is
justified, rather than something Day 13 recomputes independently.

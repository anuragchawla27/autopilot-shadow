# 13 — Disagreement, Exception Handling, Approval Gates (Day 11)

## 1. What this component does — Sections 16, 17, 18

Three related pieces, each small and deliberately built on top of what
already exists rather than recomputing it:

- **Section 16 — disagreement investigation**: when human and AI don't
  match, produce a written record (never a silent overwrite).
- **Section 17 — exception detection**: `IF confidence < threshold OR
  required_data_missing OR conflicting_information_detected THEN
  HUMAN_REVIEW`.
- **Section 18 — human-in-the-loop control**: four explicit gate
  outcomes — APPROVE, EDIT, REJECT, ESCALATE — and the human decision
  must never be bypassed.

## 2. Built on Days 9 and 10, not recomputed

`exceptions/disagreement.py` takes Day 9's per-step comparison
(`human_value`, `ai_value`, `ai_confidence`) and Day 10's risk score
(`risk_score`, `recommendation`, `reason`) for the exact same
`(resume_id, action)` pair, and assembles them into Section 16's record
shape. The only genuinely new logic is `_guess_reason` — a short,
rule-based guess at *why* the two sides might differ (tool mismatch?
data mismatch? borderline decision?), grounded only in which dimension
of the Day 9 comparison actually disagreed. It never claims certainty,
matching the brief's own example ("Potential reason: Skill synonym
interpretation" — a plausible guess, not a proven cause).

`exceptions/detector.py` implements Section 17's rule directly. A hard
failure (an exception already attached by Day 3's fault injection,
surfaced through Day 8) is the strongest signal and is passed through
as-is. A new, softer signal — confidence below Section 21's own
illustrative 70% threshold, with no hard failure — is this module's own
addition. `required_data_missing` is checked directly (success result,
empty output, for the two data-extraction actions).
`conflicting_information_detected` is checked via an explicit flag an
event's `input` can carry.

**Honest caveat on that last trigger:** no demonstration in this
project's 12-resume dataset was ever generated with genuinely
conflicting information, so the real-data run reports zero cases of
this specific trigger firing. The check itself is real and tested
(`test_conflicting_information_flag_detected` proves it fires given the
flag) — it just has nothing to catch in this dataset, the same honest
situation as Day 9's disagreement count.

## 3. The approval gate — and what it's built to prevent

`exceptions/approval_gate.py` splits Section 18 into two steps on
purpose: `gate_for()` only decides whether a case *needs* a gate (read
from Day 10's recommendation — anything other than `automate`), and
`apply_decision()` is the only function in the entire codebase allowed
to move a case out of PENDING, and it always requires an explicit
`decision` argument supplied from outside. There is no default and no
code path that reaches `"approved"` without that argument.

This is proven structurally, not just asserted in a docstring:
`test_automated_recommendation_can_never_become_approved_state_on_its_own`
parses `approval_gate.py`'s own source with Python's `ast` module and
confirms the string `"approved"` appears nowhere in the file except
inside `apply_decision`'s own function body — so nothing upstream
(the risk model, the exception detector, the queue builder) can ever
silently approve anything, by construction, not by convention. The same
AST technique proves `disagreement.py` cannot silently overwrite the
human decision either: it has no import path to `logger/human_demo.py`
or any mock-environment write method at all.

**Why zero disagreement records is honest, not a bug:** same reasoning
as Day 9/D-043 — the human policy and the AI logic were written by the
same person from the same rules, so there is no real independent human

(`test_builds_record_from_a_synthetic_mismatch`), the same pattern used

confidence-0.40 cases), 2 `human_review` failed extractions. 16 matches
Day 10's own recommendation counts exactly — the gate doesn't invent a
different number, it reads Day 10's.

## 6. What Day 12 builds on top of this

Day 12 (correction memory and workflow versioning, Sections 24-25)
reads `results/day11_disagreements.json` and whatever `apply_decision`
outcomes get recorded as the actual "Stored Correction Data" Section 24
asks for (Original AI Decision, Human Correction, Evidence, Workflow
Context, Reason, Timestamp) — this day's disagreement records and
approval outcomes are exactly that data, not something Day 12 needs to
regenerate.

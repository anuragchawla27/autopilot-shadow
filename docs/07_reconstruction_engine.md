# 07 — Workflow Reconstruction Engine (Day 5)

## 1. What this component does

Section 6 of the brief: "transform raw workflow demonstrations into a
structured workflow" by identifying relationships between events. This
engine reads `data/demonstrations.json` (Day 4's 79 events across 15
demos) and produces exactly one `Workflow` object (Day 2 schema).

## 2. Scope boundary (deliberate, see docs/03)

This stage only recovers **structure** — steps and their order/branches.
It does not:
- classify steps into automate/human_review/etc. (Day 7's job),
- label rules explicit/inferred/unknown (Day 6's job),
- compute risk (Day 10's job).

Every step comes out with `step_type=unclassified`, `risk=unknown`,
`classification_reason=None` — verified directly by
`test_unclassified_steps_have_no_premature_labels`. This matters: mixing
structure discovery with classification would make it impossible to
later audit which stage actually produced which judgment.

## 3. Algorithm (our own design — not a claim of established process-mining technique)

1. Group the flat event list back into per-demo sequences, ordered by
   `step_index`.
2. **Exclude `demo_dup_*` and `demo_fault_*` demonstrations first**
   (`filter_structural_demos`) — see decision D-022 below. These Day 4
   demos deliberately contain artificial post-completion or
   fault-injected events for exception-handling testing, not organic
   workflow shape.
3. Walk the remaining demos and build a directed graph: an edge
   `action_A -> action_B` exists whenever `B` was observed immediately
   after `A` within the same demo. A demo that failed on a step
   contributes no edge past that point (nothing observably happened
   after it).
4. Each distinct **action name** becomes exactly one `WorkflowStep` —
   `classify_candidate` from 12 different demos becomes ONE node, not 12.
   This is the actual "reconstruction": a union of per-demo sequences
   into one structure, not a replay of the logs.
5. A step's `application` field is the majority-vote application value
   observed for that action.
6. The entry step is whichever action most demos actually started with.

## 4. Why the dup/fault demos had to be excluded (D-022)

Without the filter, the duplicate-submission demo's extra step (a second
`fetch_resume` call appended *after* a fully completed, successful run)
creates a nonsensical edge: `send_interview_invitation -> fetch_resume`.
This is proven directly, not just asserted: `test_including_dup_and_fault_demos_would_pollute_the_graph`
runs reconstruction on the **unfiltered** event list and confirms that
spurious edge actually appears. The fix is a visible, one-line filter
call, not a change to the graph algorithm itself — the dup/fault demos
are the right tool for Day 11's exception-handling work, just the wrong
input for structural reconstruction.

## 6. An honest null finding

`update_candidate_record`'s continuation to `send_interview_invitation`
is **optional**, not a fork to a different named action — some
demonstrations (reject / human_review) simply end at
`update_candidate_record`; they don't branch to a *different* action.
Because our graph model only creates a branch when a step has 2+
*distinct* next actions, this dataset genuinely has **zero multi-way
branches** (`num_branch_steps == 0`). This is reported as a real result
in `results/day05_reconstruction_stats.json`, not glossed over — our
test suite explicitly checks and confirms this null finding
(`test_reconstruction_stats_reasonable`), and a separate test
(`test_update_candidate_record_continuation_is_optional_not_a_true_branch`)
confirms directly against the raw events that some demos terminate at
`update_candidate_record` while others continue.

**Implication for Day 7:** true conditional branching (e.g. shortlist vs
reject as genuinely different downstream paths) will need to come from
the *rules* attached to `classify_candidate` (Day 6's decision
extraction), not from this stage's action-adjacency graph. The
reconstruction engine correctly tells us the workflow's action sequence
is linear with an optional tail — the branching logic lives in the
decision, not in the step graph.

## 8. What Day 6 builds on top of this

Day 6's decision-extraction engine reads this same `demonstrations.json`
(the full, unfiltered set — decision rules can and should be learned
from every demo, including edge cases) plus this reconstructed
`Workflow`, and fills in `Rule.rule_type` (explicit/inferred/unknown) on
the `classify_candidate` step, using the `DecisionRecord.evidence`
already captured in each event's `decision` field back in Day 4.

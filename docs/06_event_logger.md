# 06 — Workflow Event Logger (Day 4)

## 1. What this component does

Turns real calls into the Day 3 mock environment into Day 2 `Event`
records — the exact "set of historical workflow demonstrations" Section 5
of the brief requires as input. Nothing here decides workflow logic;
`EventLogger.log_action` only records what happened, successfully or not.

## 2. Design: record vs decide

`EventLogger` (`logger/event_logger.py`) never chooses what action to take
next — it only wraps a call and turns the outcome into an `Event`, catching
`MockToolError` and related exceptions and converting them into a
structured `ExceptionRecord` instead of letting the demo crash.

The decision of *which* action to take is a separate module,
`HumanDemoPolicy` (`logger/human_demo.py`), because the exact same logger
will later wrap the AI shadow engine's actions on Day 8 with zero changes
— only the "who decides what to do next" layer differs between a human
demo and an AI shadow run.

## 3. Human demo policy (`logger/human_demo.py`)

Implements the Section 5 step sequence exactly:

```
fetch_resume → extract_resume → check_experience → compare_skills
→ classify_candidate → update_candidate_record → [send_interview_invitation if shortlisted]
```

**What is established rule vs our own design (per `docs/03`):**

| Rule | Type | Source |
|---|---|---|
| `experience_years < required_experience → reject` | Explicit | Verbatim from Section 8 of the brief |
| Skill-match tiers (full / partial / none / no-data) driving `shortlist` / `human_review` | Our own design | Authored to generate varied, realistic synthetic outcomes; **this is data-generation policy, not a claimed learned rule** — Day 6's decision-extraction engine is what re-derives rules from these demonstrations, and must not be confused with this generator |
| Prompt-injection override → always `human_review` | Our own design | Demonstrates Safety rule S5 (resume text is data, never instructions) with a narrow, known pattern match — not a general content filter |

This distinction matters: the policy that *generated* the demo data is
not the same thing as the decision-extraction engine that will later
*read* it and infer rules on Day 6. Conflating them would make Day 6's
"accuracy" trivial (it would just be re-discovering its own generator).

## 5. Dataset generated (`data/demonstrations.json`)

`logger/build_dataset.py` runs the policy over all 12 resumes plus two
extra scenarios, producing **79 events across 15 demonstrations**:

| Demo group | Count | Purpose |
|---|---|---|
| One demo per resume (`demo_0001`…`demo_0012`) | 12 demos, 66 events | Normal per-resume runs; res_0009/res_0010 stop early with a structurally-detected exception (no fault injection needed) |
| `demo_dup_0001_res_0011` | 1 demo, 8 events | Forces a second fetch of the same resume → `DuplicateResumeAlreadyFetched`, logged as a failure Event (Section 23 Case 8) |
| `demo_fault_tool_failure` | 1 demo, 1 event | Injected `TOOL_FAILURE` on fetch — demo stops immediately, logged as failure |
| `demo_fault_malformed_parse` | 1 demo, 2 events | Injected `MALFORMED_INPUT` on the parse step for an otherwise-clean resume |

Result breakdown: **74 success events, 5 failure events** — generated by
running the actual code, not hand-typed (Safety rule S7).

## 7. What Day 5 builds on top of this

`data/demonstrations.json` is the raw input the reconstruction engine
(Day 5) will read to produce a `Workflow` (Day 2 schema) — grouping these
per-demo event sequences into one structured, de-duplicated workflow
definition.

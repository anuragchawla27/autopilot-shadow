# 09 — Automation Generator (Day 7)

## 1. What this component does

Section 9 (classify every step into 5 categories, by **explicit
criteria**) and Section 11 (generate an executable automation spec).
This is the first component that actually decides "how much can we
automate here" — everything before this (Days 5-6) only recovered facts
about the workflow; this is the first judgment call, and it has to be
defensible, not arbitrary.

## 2. The classifier (Section 9)

`generator/classifier.py` applies 6 criteria, in a fixed order, to every
step of `data/workflow_with_decisions.json` (Day 6's output). Every step
comes out with a non-blank, specific `classification_reason` — verified
by a test that rejects placeholder-length reasons.

| Step | Classification | Why (in brief) |
|---|---|---|
| `fetch_resume` | AUTOMATE | No rules, pure read, reversible, low risk |
| `extract_resume` | AUTOMATE | No rules, pure parsing, reversible, low risk |
| `check_experience` | AUTOMATE | No rules, plain numeric comparison, no ambiguity |
| `compare_skills` | **AUTOMATE_WITH_MONITORING** | No rules, but named exception: Section 4's table explicitly calls out skill matching for monitoring, and res_0004 (Day 4/6) is direct proof why — keyword matching misses synonyms |
| `classify_candidate` | HUMAN_REVIEW | 6 rules attached (Day 6): 2 explicit, 4 unknown — mixed evidence means some paths are understood, others aren't |
| `update_candidate_record` | AUTOMATE | No rules of its own; does NOT inherit the upstream step's uncertainty (see §4) |
| `send_interview_invitation` | HUMAN_REVIEW | Criterion 1 fires first: irreversible + external-facing, Section 22's safety override applies regardless of rule evidence |

Generated by running the code:
```
$ python -m autopilot_shadow.generator.build_automation
  fetch_resume                 -> automate            (risk=low)
  extract_resume               -> automate            (risk=low)
  check_experience             -> automate            (risk=low)
  compare_skills               -> automate_with_monitoring (risk=low)
  classify_candidate           -> human_review        (risk=medium)
  update_candidate_record      -> automate            (risk=low)
  send_interview_invitation    -> human_review         (risk=high)
```

No step comes out BLOCKED in this dataset — `classify_candidate` has a
mix of explicit and unknown rules (not *all* unknown), so it correctly
lands on HUMAN_REVIEW rather than BLOCKED. This is itself a check: the
classifier doesn't default to the scariest label just because some
evidence is thin.

## 3. A real mismatch I caught against the brief's own table

Section 4 lists "Skill matching: Automatable with confidence monitoring"
as distinct from "Experience calculation: Potentially automatable."
A classifier built from "has rules? no? -> AUTOMATE" alone would have
missed that distinction entirely, since neither `compare_skills` nor
`check_experience` has a `Rule` object attached (Day 6 only attached
rules to the final `classify_candidate` decision). I added a small,
named, documented exception set (`MONITORED_COMPUTATION_ACTIONS`) rather
than silently hard-coding one line — and justified `compare_skills`'
inclusion with our own observed evidence (the res_0004 synonym
mismatch), not just by copying the brief's table uncritically.

## 4. A deliberate design point: risk does not flow backward

`update_candidate_record` has no rules of its own, so it gets AUTOMATE —
even though it writes the output of `classify_candidate`, a HUMAN_REVIEW
step. This is intentional: by the time this step runs, the status has
already been through `classify_candidate`'s own gate (once Day 11 builds
real approval handling). Recording an already-resolved value is a
separate, low-risk action; it is not re-deciding anything, so it
shouldn't inherit the upstream step's uncertainty label.

## 5. D-004 resolved: custom DAG runner, not LangGraph

`generator/executor.py` is the executable spec Section 11 asks for —
proof that the Workflow (with classifications) can actually run, not
just be drawn. Rather than adopt LangGraph, I built a small (~80-line)
runner directly over our own `Workflow` schema, because:

- Day 5 already found this workflow has no true multi-way branch — a
  general graph-orchestration framework has no complexity here to earn
  its keep.
- The executor's actual job for the rest of the project is precise,
  auditable **step-level halting**: stop exactly at a HUMAN_REVIEW/
  BLOCKED step and hand off to an approval gate (Day 11), then later
  intercept every tool call for shadow mode (Day 8) — both achieved
  directly by reusing Day 4's `EventLogger` unchanged.
- Section 34 explicitly asks us to avoid unnecessary complexity and
  justify every tech decision.

This closes the open item from Day 1's decision log (D-004).

## 6. Proof the spec is actually executable

`generator/handlers.py` implements each action generically (not a
hardcoded sequence — the executor looks up the handler by whatever
action the Workflow graph visits next), reusing the SAME mock-tool calls
as Day 4. Two real dry runs, generated by the code:

```
res_0001 (clean full match): 5 events, halted at action='classify_candidate' approval='pending'
res_0004 (skill synonyms, ambiguous): 5 events, halted at action='classify_candidate' approval='pending'
```

Both runs actually executed `fetch_resume → extract_resume →
check_experience → compare_skills` against the real mock environment
(confirmed: `res_0001` is marked processed in `ResumeDatabase` afterward
— this is a real side effect, not a stub) and then halted with a
`PENDING` approval event, never silently finalizing the decision or
reaching `update_candidate_record`/`send_interview_invitation`.

## 7. An honest finding: both resumes halt at the same place

res_0001 (unambiguous, strong match) and res_0004 (genuinely ambiguous,
synonym mismatch) **halt at the exact same step**. This is not a bug —
Section 9 asks the system to classify *steps*, not individual cases.
Our classifier is step-level by design, so a step with any
non-explicit-only evidence (`classify_candidate`) halts for every case
that reaches it, easy or hard alike.

**What this hands to later days:** per-instance confidence routing —
letting an easy case like res_0001 proceed while a genuinely hard one
like res_0004 still halts — is explicitly Day 10 (confidence/risk
scoring) and Day 11 (approval gates) territory, not Day 7's. Keeping
this boundary explicit means each day's contribution can be tested
separately, rather than Day 7 quietly reaching ahead into work it
shouldn't own yet.

## 8. A small, backward-compatible change to Day 4's EventLogger

Attaching a handler-computed `DecisionRecord` to the right Event hit a
real chicken-and-egg problem: the decision is only known once the
handler runs, but `log_action`'s `decision` parameter is normally set
before `fn()` executes. Rather than hack around it with mutable closures
(which I tried first and caught as buggy before committing it), I added
an optional `decision_from_result=True` flag to `EventLogger.log_action`:
when set, `fn()` returns `(output, decision)` instead of just `output`.
Day 4's existing calls don't pass this flag, so nothing about Day 4
changed — confirmed by all 18 of Day 4's tests still passing.

## 9. A refactor for honest code-sharing

While wiring up `handlers.py`, I needed the same skill-matching and
prompt-injection-detection logic Day 4's `human_demo.py` already had —
but those were private (underscore-prefixed) functions. Reaching into
another module's internals is bad practice, so I moved them to a new
shared module, `common/feature_utils.py`, imported publicly by both
files. This is a different kind of sharing from the Day 6 independence
requirement (D-027): extraction must not import the *decision-outcome*
logic it's trying to independently verify, but sharing *how a feature is
computed* (skill overlap arithmetic) is fine and avoids duplicating the
same formula in two places.

## 11. What Day 8 builds on top of this

Day 8's shadow execution engine reuses `generator/handlers.py` and the
same `AutomationExecutor` pattern, but instead of halting and waiting at
a human gate, it runs the AI's proposed action **alongside** the human's
real action (from `demonstrations.json`) without ever executing an
irreversible step, and records what the AI *would have done* for the
comparison engine (Day 9) to use.

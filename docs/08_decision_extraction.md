# 08 — Decision & Condition Extraction (Day 6)

## 1. Why this day exists (the question you asked)

Day 5 recovered *order* — the shape of the workflow. It said nothing
about *why* a candidate ends up shortlisted vs rejected vs sent for
human review; that logic was buried inside Day 4's `human_demo.py`,
which is code WE wrote to generate realistic fake data, not a
discovered rule.

Section 8 of the brief makes it **mandatory** that the system itself
look at the demonstrations and label every decision rule it finds as
exactly one of:

- **EXPLICIT** — stated directly by the workflow / business configuration.
- **INFERRED** — not stated anywhere, but consistent across repeated examples.
- **UNKNOWN** — not enough evidence, or contradictory evidence, to say confidently.

This exists because Section 29's priority metric is **false automation
rate**: automating a step whose real rule was never actually
understood. If we let "inferred" quietly become "as good as explicit"
whenever a pattern merely looked consistent, we'd be building exactly
the failure mode the whole project is designed to catch. Day 6 is the
guardrail against that.

## 2. Critical design requirement: genuine independence from Day 4

Day 4's `HumanDemoPolicy` is the code that decided what each synthetic
demo should do, so synthetic data could exist at all. If the extraction
engine built on Day 6 simply imported or re-implemented that same logic,
"discovering" its rules would be circular — it would just be reading
its own notes back to itself.

So `decisions/extraction.py` reads **only**:
- `data/demonstrations.json` (the logged events — what actually happened)
- `data/job_description.json` (the one piece of explicit business config)

It has **no import of `human_demo.py`**, proven structurally by parsing
the module's AST and checking its import list
(`test_extraction_does_not_import_human_demo_policy`), not just by a
promise in a comment.

## 3. Labelling algorithm (our own design — see docs/03)

| Label | Rule |
|---|---|
| EXPLICIT | The condition maps directly onto a field already configured in `job_description.json` (`required_experience_years`, `required_skills`) — matching Section 4's "explicit policy configuration" and Section 8's own worked example (`required_skill_present`). |
| INFERRED | Not backed by explicit config, but the SAME evidence combination produced the SAME outcome in **2 or more** independent demonstrations. |
| UNKNOWN | Either only 1 supporting example (not enough to generalize) or the same evidence combination produced DIFFERENT outcomes across demos (contradictory). |

We deliberately did **not** set the INFERRED threshold at 1 example.
With only 12 demonstrations, almost every specific edge case only
occurs once — calling a single occurrence "inferred" would be
fabricating confidence the data doesn't support (Safety rule S7,
Section 38).

## 5. The honest finding: zero rules came out "inferred"

This is the most important result of the day, and it is **not** a bug —
it's exactly what Section 38 asks for ("if automation readiness remains
low, document it"). Every edge-case pattern (partial skill match,
no extractable skills, zero keyword match, the prompt-injection case)
occurred in only **one** demonstration each. The engine correctly
refuses to call any of them "inferred" and reports them as UNKNOWN —
insufficient evidence to generalize — rather than quietly promoting a
single example to a confident rule.

**What this means for the project going forward:** with only 12 synthetic
resumes, this workflow does not yet have enough evidence to support
automation of the ambiguous middle ground (partial matches, missing
data, terminology mismatches). Only the two extremes — clearly
insufficient experience, and a full, unambiguous match — are backed by
explicit configuration. Day 13's readiness assessment will need to
reflect this: readiness should come out **low for the ambiguous cases**,
not an artificially high number.

## 6. A specific, flagged finding: the prompt-injection case

The res_0012 override (forcing `human_review` whenever suspicious text
is detected) is labelled **UNKNOWN**, with 1 supporting example. This is
correct *from the extraction engine's point of view*: it only has access
to events and explicit JD config, and the injection-handling policy
isn't declared anywhere it can check. It cannot tell the difference
between "a real safety rule we should trust" and "something that
happened to occur once." This is flagged as an open design question for
later days — Section 17 (exception detection) may be the right place to
make injection-handling an explicit, declared policy rather than an
implicit one.

## 8. What Day 7 builds on top of this

Day 7's automation generator reads `data/workflow_with_decisions.json`
and uses each step's rule evidence (not just presence/absence of a rule)
to decide the 5-way automation classification
(automate / automate_with_monitoring / human_review / human_only /
blocked) — explicit, well-evidenced rules can support more automation;
UNKNOWN rules should push toward human_review or blocked, by explicit
criteria rather than guesswork, per Section 9.
